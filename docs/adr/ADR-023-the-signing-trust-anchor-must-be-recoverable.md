# ADR-023 — The signing trust anchor must be recoverable (extends ADR-022)

**Status:** Accepted — clause 3's fallback **corrected by VERIFY**; recovery key outstanding
**Extends:** ADR-022
**Source:** owner decision, 2026-09-03

---

**Problem:** a fleet enforcing "signed by exactly one key" is unrecoverable if that
key is lost or must be revoked — you cannot sign the very image that would
introduce its replacement. For an auto-updating OS that is a **permanent
fleet-wide loss of the update path**: worse than a bad update, because a bad
update rolls back and you ship a fix, whereas a lost key means you cannot ship the
fix. A backup of the same key does not solve compromise — a leaked key stays
leaked. Recovery requires a **distinct, trusted-but-unused** key.

**Decision:**

1. From the first `:stable` image, `policy.json` trusts a **set**: {primary,
   recovery}. Primary = the CI key, human-gated per ADR-022. Recovery = a distinct
   keypair whose private half lives **offline in cold storage**, never in CI or any
   secret store, used only in a manual, high-ceremony incident.
2. **Introduction/rotation protocol** (runbook, required before any key change): a
   new trusted key is introduced by an image signed with an **already-trusted**
   key; the fleet must adopt that image **before** the new key is ever used to
   sign. The self-verify check catches the single mistake; this protocol prevents
   the ordering hazard.
3. Policy accepts if signed by **any** trusted key (OR semantics), giving every
   rotation a safe overlap window where both old and new signatures verify.

**Consequence:** primary loss or compromise is recoverable without bricking the
update path. Generating the recovery keypair and adding its public half to
`policy.json` is a **WP-04 signing deliverable that gates the first `:stable`** —
not M0. Recovery-key custody is an owner responsibility documented in the runbook.

---

## VERIFY results (2026-09-03)

### Clause 3 is implementable — but its stated fallback is not

`keyPaths` and `keyDatas` (plural) are supported by containers-common 0.67.0, so
one `sigstoreSigned` requirement can name a set of keys. That is the mechanism.

**The fallback in clause 3 — "parallel policy requirements" — would not work, and
would fail in a dangerous direction.** Multiple requirements within a transport
scope are **ANDed**, verified directly:

```
scope: [ {insecureAcceptAnything}, {reject} ]   ->  REJECTED
```

If that were OR, an accept-anything requirement would have carried it. So two
`sigstoreSigned` requirements side by side would demand **both** signatures — the
exact opposite of the overlap window clause 3 exists to create, and it would
brick every rotation rather than smooth it. The comment in `policy.json` says so
at the point where someone would be tempted to write it.

### A second half of the client side that we were not shipping

A correctly signed image was **rejected** with "A signature was required, but no
signature exists" until `registries.d` opted in:

```yaml
docker:
  ghcr.io:
    use-sigstore-attachments: true
```

containers-image does not fetch sigstore attachments without it. `policy.json`
alone is **not** the client half of signing; without this file the policy rejects
every image, on every machine, at once. Now shipped as
`os/rootfs/etc/containers/registries.d/meridian.yaml`.

### Not established: whether `keyPaths` means ANY or ALL

The harness could not get containers-image to read a signature that cosign
**v3.1.3** had written, so the semantic question behind clause 3 is **unproven**.

The cause looks like a version incompatibility worth pinning down before it
reaches CI: cosign v3 wrote its signature to a tag named `sha256-<hex>` while
containers-image looks for `sha256-<hex>.sig`, even with
`--registry-referrers-mode=legacy`. If that reproduces in CI, **images we sign
will not verify on the machines that receive them** — the failure would appear as
"signing is broken everywhere" rather than as a version mismatch.

This is exactly what ADR-022's negative test is for, and it is a further reason
that gate must pass before the first `:stable` rather than being assumed. Two
things must be settled there:

1. pin a cosign version whose output containers-image reads, and assert it;
2. confirm `keyPaths` accepts an image signed by **any one** of the listed keys —
   because if it means ALL, clause 3's overlap window does not exist and the
   rotation protocol in clause 2 needs redesigning.

**Consequences:**

- The fleet currently trusts **one** key and is therefore **not recoverable**.
  That is the state ADR-023 exists to end, and it is why the recovery key gates
  `:stable` rather than being deferred to a later milestone.
- The recovery key cannot be generated by an agent or by CI. It is an owner
  action, offline, and its custody is the owner's — a key held anywhere a
  compromise could reach is not a recovery key, it is a second primary.
